# 一句话成片旧架构清理分阶段执行方案

版本：2026-07-28  
适用范围：`D:\project\RenYiMen` 一句话成片工作流  
目标：把当前“新队列包裹旧执行函数”的过渡架构，迁移为单一合同、单一状态源、单一任务图、可恢复的 durable worker 架构。

---

## 1. 最终目标

清理完成后，系统必须满足以下约束：

1. `VideoProductionJob` 是生产任务唯一状态权威。
2. `VideoProviderTaskLease` 只表达上游容量占用，不表达业务阶段。
3. `VideoGenerationCandidate` 只表达候选结果，不驱动项目阶段。
4. Keyframe、Segment 上的状态只是 Job 状态的只读投影，不参与调度决策。
5. 所有生成任务必须具有非空 `targetId` 和稳定 `artifactId`。
6. 执行合同只保存英文 canonical contract；中文只作为界面展示数据。
7. `segments + keyframes` 是唯一生产实体，不再向前端伪装为 `shots`。
8. Artifact tables 是执行数据唯一权威；`planJson` 只保留规划快照或最终废弃。
9. 规划、图片、子分镜、视频、质量检测、合成都通过 durable jobs 执行。
10. `/resume` 不再猜测下一步，只执行后端返回的单一 `recoveryAction`。
11. Worker 必须通过 payload schema 和 runtime version 握手后才能领取任务。
12. Web/Worker 发布期间不得因热更新中断正在运行的任务。

目标状态：

```text
用户操作
   ↓
Command API
   ↓
Task Graph / VideoProductionJob
   ↓
Worker（按 kind 消费）
   ↓
Provider Lease（仅容量控制）
   ↓
Generation Candidate（仅结果）
   ↓
Artifact Tables（执行事实）
   ↓
Project Projection / UI
```

---

## 2. 执行原则

### 2.1 禁止在真实任务运行时修改核心编排代码

当前本地 Worker 使用 `--watch`。修改核心文件会重启 Worker，使已经领取的 job 留下未回收 lease。

执行代码迁移前必须：

1. 停止接收新的一句话成片任务。
2. 等待现有 job 进入终态，或明确标记为暂停迁移。
3. 停止 Web 和全部 Worker。
4. 完成代码、数据库迁移和测试。
5. 使用固定构建产物重新启动，不使用 `--watch` 执行验收任务。

禁止边跑生产项目边修改：

- `project-service.ts`
- `production-job-queue.ts`
- `three-stage-planner.ts`
- provider capacity/lease 代码
- worker 脚本
- Prisma Schema

### 2.2 每个阶段必须独立可验收

不得一次性删除全部兼容层。每阶段必须做到：

- 有明确数据库不变量。
- 有自动化测试。
- 有可观测指标。
- 有上线门禁。
- 有回滚方式。

### 2.3 先停止错误行为，再做数据迁移

顺序必须是：

1. 停止任务风暴和同步提交。
2. 建立单一 job 状态机。
3. 建立严格合同和 target 约束。
4. 迁移 Artifact 权威数据。
5. 迁移前端实体语义。
6. 最后删除数据库旧表和死代码。

---

## 3. 阶段总览

| 阶段 | 目标 | 风险 | 是否涉及数据库 |
|---|---|---:|---:|
| Phase 0 | 冻结运行环境和建立基线 | 低 | 否 |
| Phase 1 | 封闭 P0 旧执行入口 | 中 | 少量 |
| Phase 2 | 统一 durable job 状态机 | 高 | 是 |
| Phase 3 | 强制 targetId、合同和 Worker 版本 | 高 | 是 |
| Phase 4 | Checkpoint 可迁移、禁止从头重跑 | 中 | 可能 |
| Phase 5 | Artifact tables 成为唯一权威 | 高 | 是 |
| Phase 6 | 前端切换为 segments/keyframes/taskGraph | 中 | 否 |
| Phase 7 | 拆除万能 `/resume` 和字符串错误协议 | 中 | 是 |
| Phase 8 | 删除旧表、旧字段、旧 API 和死代码 | 高 | 是 |
| Phase 9 | 灰度、压测和生产切换 | 高 | 是 |

# Phase 0：冻结运行环境并建立迁移基线

## 目标

避免迁移期间 Worker 热重启、状态继续变化，保留可比较的迁移前数据。

## 执行步骤

1. 在界面关闭“一句话成片”新建和继续生成入口。
2. 停止 `scripts/dev-with-video-worker.mjs`。
3. 确认没有以下进程：
   - `next dev`
   - `video-production-worker.ts`
   - 项目相关 `ffmpeg`
4. 备份数据库。
5. 导出以下表的数量和状态分布：
   - `video_projects`
   - `video_production_jobs`
   - `video_provider_task_leases`
   - `video_generation_candidates`
   - `video_keyframes`
   - `video_segments`
   - `video_shots`
   - 全部 artifact tables
6. 导出所有非终态 job、lease、candidate。
7. 建立迁移前基线报告。

## 必须记录的指标

```text
queued/running production jobs
waiting/reserved/running provider leases
pending/running/evaluating candidates
project_reconcile 总数
target_id IS NULL 数量
FINAL_REVIEW/DONE 项目上的非终态任务数量
artifact table 每表记录数
planJson 同时包含 shots/segments/keyframes 的项目数量
```

## 验收门禁

- 核心代码修改期间不存在运行中的生成任务。
- 数据库备份可恢复。
- 已记录迁移前统计。

## 回滚

Phase 0 不修改数据，重新启动旧版本即可。

# Phase 1：封闭 P0 旧执行入口

## 目标

先阻止新项目继续进入旧执行路径。

## 1.1 删除旧规划 fallback

涉及文件：

- `src/services/video-orchestrator/three-stage-planner.ts`

要求：

- split planner 失败后只允许：
  - 局部 repair；
  - 从兼容 checkpoint 恢复；
  - 返回结构化失败。
- 禁止调用旧整包规划器。
- 删除默认开启 fallback 的配置。
- 日志中不得再出现 `legacy_fallback`。

验收：

- 人为制造 split schema 错误。
- 系统只能进入 `contract_repair_required` 或局部 repair。
- 不得产生第二套完整规划调用。

## 1.2 禁止内部吞掉容量异常

涉及文件：

- `project-service.ts`
- `provider-capacity.ts`
- provider adapter 调度代码

要求：

- `CAPACITY_EXHAUSTED`、`LEASE_UNAVAILABLE` 必须抛回 Worker。
- Worker 根据结构化错误设置 `availableAt`。
- micro-shot 和 clip 内部不得捕获后返回“生成中”。
- 同一 target 同一 revision 只能存在一个活动 job。

验收：

- 将 provider 容量设置为 0。
- job 必须保持同一 ID 并延迟重试。
- 不得创建新的 reconcile 或新的同 target job。

## 1.3 删除全局 reconcile 扫描器

要求：

- 删除 `project_reconcile` job kind。
- 删除全局项目状态扫描。
- 删除 `pumpGlobalVideoProviderQueue` 及 alias。
- 上游轮询由原 target job 自己执行：

```text
queued → preparing → submitted → generating → completed
```

- 同一个 durable job 在轮询时只更新 `availableAt`，不得生成新的 job。

迁移：

- 历史 `project_reconcile` 全部标记为 cancelled/archived，或移入历史表。
- 不允许重新执行历史 reconcile。

验收：

- FINAL_REVIEW/DONE 项目 30 分钟内新增 reconcile 数量必须为 0。
- 同一 target 上游轮询期间 production job 数量始终为 1。

## 1.4 手动重新生成必须入队

涉及接口：

- Keyframe regenerate
- Micro-shot regenerate
- Segment clip regenerate

要求：

- Web API 只校验、创建 revision、enqueue job，然后返回。
- Web API 不得直接调用 provider。
- Web API 不得等待生成完成。

验收：

- 请求在 2 秒内返回。
- 关闭 Web 进程后 Worker 仍能完成任务。

## 1.5 禁止缺合同自动构造旧合同

要求：

- 缺少 canonical contract 时返回：

```json
{
  "errorCode": "EXECUTION_CONTRACT_MISSING",
  "recoveryAction": "REPAIR_CONTRACT"
}
```

- 禁止运行时构造 legacy video prompt contract。
- 禁止损坏项目越过 gate 提交 provider。

## Phase 1 验收

- 新项目不会触发旧整包规划器。
- 没有新 `project_reconcile`。
- 容量不足只重排同一个 job。
- 手动生成全部经过 Worker。
- 缺合同不会提交上游。

# Phase 2：统一 durable job 状态机

## 目标

彻底解决“job 完成、lease 等待、candidate 成功、实体仍 running”的状态分裂。

## 2.1 定义唯一生产状态机

建议 job 状态：

```text
queued
claimed
running
waiting_upstream
waiting_review
completed
failed
cancelled
```

建议 job stage：

```text
planning
contract_validation
provider_submission
provider_polling
quality_evaluation
composition
```

禁止混用：

- `status=completed, stage=generating`
- `status=completed, stage=submitted`
- `status=failed` 但项目仍无错误或 recovery action

## 2.2 明确三类表职责

### VideoProductionJob

负责：

- 当前是否还有工作。
- 重试次数。
- 下一次执行时间。
- 错误分类。
- Worker lease。
- 项目阶段推进。

### VideoProviderTaskLease

只负责：

- provider/resource 容量占用。
- 上游 task ID。
- lease 过期和释放。

不得负责：

- 项目状态。
- UI 进度。
- 是否需要创建新任务。

### VideoGenerationCandidate

只负责：

- 候选媒体。
- 质量结果。
- 用户选择。

不得负责：

- 调度下一 target。
- 判定项目是否仍在生成。

## 2.3 项目状态改成只读投影

增加统一 projector：

```text
projectProductionProjection(projectId)
```

投影只能从以下来源计算：

1. 非终态 ProductionJob。
2. 待用户审批节点。
3. 已完成 artifact 数量。
4. task graph 当前 frontier。

严禁从以下字段推断：

- `imageTaskId`
- `clipTaskId`
- `composeTaskId`
- candidate 是否存在
- lease 是否 waiting

## 2.4 增加终态不变量

必须自动检测：

```text
project.status = *_GENERATING
AND active production jobs = 0
```

处理规则：

- 存在失败 job：项目进入 `FAILED` 或 `WAITING_RECOVERY`。
- 存在待审批 artifact：项目进入对应 review 状态。
- 所有 artifact 完成：推进下一 task graph 节点。
- 无法判定：进入 `STATE_INVARIANT_VIOLATION`，禁止假装运行中。

## Phase 2 验收

- 不再出现“active job 为 0，但项目显示生成中”。
- 项目状态可以仅通过 job/task graph 重建。
- lease/candidate 状态变化不会直接改变项目阶段。

# Phase 3：强制 targetId、执行合同和 Worker 版本

## 目标

让错误任务不能进入队列，让旧 Worker 不能消费新 payload。

## 3.1 targetId 数据迁移

先分类历史 null：

- planning：使用 `projectId` 作为 targetId。
- compose：使用固定 target `final`。
- target media job：必须从 artifact/entity 确定 target。
- 无法确定：标记 `migration_failed`，不得猜测第一个目标。
- 历史 reconcile：归档，不参与迁移执行。

然后数据库执行：

```sql
ALTER TABLE video_production_jobs
ALTER COLUMN target_id SET NOT NULL;
```

增加 CHECK：

```text
length(trim(target_id)) > 0
```

删除 Worker 中所有 `inferredTarget`、`first generatable target` 逻辑。

## 3.2 canonical execution contract

定义唯一版本，例如：

```json
{
  "schemaVersion": 2,
  "language": "en",
  "targetId": "...",
  "artifactId": "...",
  "revision": 3,
  "prompt": "...",
  "negativePrompt": "...",
  "constraints": {},
  "references": []
}
```

中文展示数据必须放入独立字段或独立 UI view model：

```json
{
  "display": {
    "zh": {
      "prompt": "..."
    }
  }
}
```

禁止：

```ts
imagePrompt = imagePromptZh
```

禁止中文编辑时同时覆盖 canonical execution prompt。

## 3.3 字段冲突必须报错

迁移入口允许读取旧别名，但必须先 canonicalize。

如果同时存在且值不同：

```text
segmentNo != shotNo
imagePrompt != image_prompt
consistencyManifest != consistency_manifest
```

必须返回：

```json
{
  "errorCode": "PLAN_FIELD_ALIAS_CONFLICT",
  "recoveryAction": "MIGRATE_PLAN_FIELDS"
}
```

生产执行器只接受 canonical 字段，不再自行选择优先级。

## 3.4 Worker 版本握手

job payload 必须包含：

- `payloadSchemaVersion`
- `requiredWorkerVersion`
- `contractVersion`

Worker 注册：

- runtimeVersion
- supportedKinds
- supportedPayloadVersions
- processId
- startedAt
- heartbeatAt

领取 job 时必须原子校验版本。

版本不兼容：

- 不领取任务。
- job 保持 queued。
- 输出 `NO_COMPATIBLE_WORKER`。
- UI 显示明确运维错误。

## Phase 3 验收

- 数据库不存在 null/空 targetId。
- 旧 payload 不会被新 Worker 静默执行。
- 新 payload 不会被旧 Worker 消费。
- 中文展示修改不会改变 provider prompt。
- 字段冲突会在执行前失败。

# Phase 4：Checkpoint 迁移与局部恢复

## 目标

修复代码、升级合同或改变 planner 版本后，保留仍然有效的已完成阶段。

## 4.1 Checkpoint 必备字段

```json
{
  "checkpointVersion": 14,
  "plannerMode": "split",
  "inputFingerprint": "...",
  "inputSnapshot": {},
  "completedStages": [],
  "stageOutputs": {},
  "contractVersions": {},
  "referenceFingerprint": "..."
}
```

## 4.2 建立版本迁移器

实现：

```text
migrateCheckpointV12ToV13
migrateCheckpointV13ToV14
```

禁止：

- 版本不一致直接返回空 checkpoint。
- plannerMode 改变时删除全部成果。
- 代码版本变化被计入用户输入 fingerprint。

## 4.3 定义最小失效范围

示例：

- 只改 UI 中文：不失效任何执行阶段。
- Prompt contract 版本变化：只失效 prompt compilation 及下游。
- Story 输入变化：失效 story architect 及下游。
- 参考图变化：失效 reference analysis 及依赖该参考的下游。
- Worker 版本变化：不失效规划 checkpoint。

## Phase 4 验收

- 升级 checkpoint 版本后不会重新进行参考图分析。
- 修改下游合同不会重新跑剧本架构阶段。
- 每次恢复日志明确记录 preserved/invalidated stages。

# Phase 5：Artifact tables 成为唯一执行权威

## 目标

停止 `planJson ⇄ artifact tables` 双向同步。

## 5.1 先完成一次性数据迁移

迁移流程：

1. 对每个项目读取 planJson。
2. canonicalize 字段。
3. 写入 artifact tables。
4. 对比数量、revision、hash。
5. 写入迁移 marker。
6. 迁移不完整的项目进入隔离清单。

禁止只有部分表有数据时继续静默运行。

## 5.2 切换读取权威

切换后：

- 执行器只读 artifact tables。
- `planJson` 不再覆盖 artifact tables。
- `getVideoProject()` 不得在 GET 请求中执行双向回填。
- GET 请求必须只读，不能更新项目 `updatedAt`。

## 5.3 切换写入权威

所有修改直接写 artifact tables：

- Prompt revision
- Reference selection
- Quality report
- Transition reference
- Audio assets
- Artifact dependency metadata

`planJson` 如需保留，只生成只读 snapshot：

```text
artifact tables → snapshot
```

禁止反向：

```text
planJson → 覆盖 artifact tables
```

## 5.4 删除 feature flags

删除：

- `ONE_PROMPT_ARTIFACT_TABLES_DUAL_WRITE`
- `ONE_PROMPT_ARTIFACT_TABLES_READ`

不允许 read/write 独立开关。

## Phase 5 验收

- 新建项目所有 artifact table 都有数据。
- 清空测试项目 planJson 的执行字段后，任务仍可从 artifact tables 恢复。
- 修改 planJson 不会覆盖 artifact tables。
- GET 项目接口不产生数据库写入。

# Phase 6：前端迁移到 segments/keyframes/taskGraph

## 目标

前端不再模拟旧 shots 工作流，不再自行猜测后端阶段。

## 6.1 删除前端 VideoShot 语义

删除：

- `interface VideoShot`
- `selectedShot`
- `shotNo`
- `segmentToEditorShot`
- shots 兼容输出

替换为：

- `VideoSegment`
- `VideoKeyframe`
- `selectedSegment`
- `segmentNo`

## 6.2 前端只消费 taskGraph

后端返回：

```json
{
  "taskGraph": {
    "currentNode": "...",
    "status": "...",
    "progress": {},
    "allowedActions": [],
    "recoveryAction": null
  }
}
```

前端不得再根据以下字段猜测阶段：

- locked
- imageStatus
- imageTaskId
- candidate status
- clipTaskId

## 6.3 修复继续生成进度显示

“继续生成”只能显示：

- 恢复当前节点
- 等待 Worker
- 等待审批
- 执行 recovery action

不得设置为：

```text
creating / 1%
```

## 6.4 删除客户端驱动同步

删除：

- `/sync`
- 每五秒 POST 同步

替换为：

- GET projection polling；或
- SSE/WebSocket 事件。

读取接口必须无副作用。

## Phase 6 验收

- 页面源码不存在 `VideoShot` 和 `segmentToEditorShot`。
- 页面不读取 imageTaskId/clipTaskId 判断运行状态。
- “继续生成”不会显示创建新项目。
- 后端 taskGraph 与 UI 当前阶段完全一致。

# Phase 7：拆除万能 `/resume` 和字符串错误协议

## 目标

每个用户动作只有一个确定含义。

## 7.1 拆分命令

建议命令：

```text
POST /approve-assets
POST /approve-keyframes
POST /approve-micro-shots
POST /approve-clips
POST /retry-job
POST /repair-contract
POST /continue-task-graph
POST /compose
```

`/resume` 只允许兼容旧客户端，内部必须要求明确 action，不得自行猜测。

## 7.2 结构化错误

统一错误结构：

```json
{
  "errorCode": "EXECUTION_CONTRACT_TOO_LARGE",
  "category": "contract",
  "retryable": false,
  "targetId": "...",
  "artifactId": "...",
  "recoveryAction": "REPAIR_CONTRACT",
  "displayMessage": {
    "zh": "...",
    "en": "..."
  }
}
```

前端不得匹配中英文错误文案决定行为。

## 7.3 自动终态归并

任何 job 失败时必须原子执行：

1. 释放 provider lease。
2. 更新 job errorCode/recoveryAction。
3. 更新 target projection。
4. 重建 project projection。
5. 如果没有 active job，项目不得保留 GENERATING。

## Phase 7 验收

- 同一个按钮不会执行多种业务动作。
- 错误文本修改不会影响恢复逻辑。
- 任何项目无 active job 时都处于 review、failed、done 或 waiting recovery。

# Phase 8：删除旧表、旧字段、旧 API 和死代码

## 目标

在生产流量已经完全切换后，物理删除兼容层。

## 8.1 删除数据库旧结构

确认无生产读取后删除：

- `video_shots`
- `VideoProject.shots`
- `VideoProject.composeTaskId`
- `VideoKeyframe.imageTaskId`
- `VideoSegment.clipTaskId`

删除前必须归档历史值，便于问题追踪。

## 8.2 删除旧 API

删除：

- `/shots/[shotId]`
