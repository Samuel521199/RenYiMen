## 本次真实链路暴露并修复的架构问题

1. 已审批首尾帧仍被媒体规划模型重新描述，模型会把静态尾帧写成时间过程。
   现在首尾合同由“已审批图片观察事实 + canonical boundary”确定性生成，
   模型只规划中间运动。
2. `physicallyReachable` 曾与 `requires_cut=false`、`continuous_time=true`
   和低风险路径相互矛盾。现在不可达结论必须同时提供
   `requires_cut=true` 和明确 warning，否则进入局部合同 repair。
3. 媒体规划器没有在模型边界生成 `continuous-motion-contract-v1`。
   现在只在模型边界 canonicalize 一次，下游只读取唯一合同。
4. taskGraph 曾用派生项目状态反向判断边界审批，导致 micro job 完成后重新打开
   `review:boundaries`。现在审批节点只读取 artifact 审批事实。
5. `review_ready` 视频候选没有被表示为已完成的生成节点，产生
   `STATE_INVARIANT_VIOLATION`。现在它会打开明确的 `review:clips`。
6. `VideoSegment.locked` 同时承担生成输入锁和审批锁语义。taskGraph 现在只使用
   `status=CLIP_APPROVED` 判断片段审批，不再从 `locked` 猜测。
7. `/approve-clips` 现在从 taskGraph 的 `review:clips=awaiting_review`
   校验命令，不再依赖可能滞后的项目状态字段。

上述修复均在同一项目上局部恢复，没有新建项目，也没有重新执行已完成图片或视频。

## 回滚原则

若新流量出现问题：

1. 暂停领取新 job。
2. 保留 production jobs、provider leases、candidates 和 artifact tables。
3. 回滚到上一版支持 payload v2 的新架构 Worker。
4. 使用结构化 `/retry-job`、`/repair-contract` 或
   `/continue-task-graph` 恢复。

禁止重新开启 legacy fallback、旧 shot API、旧 task 指针或全局项目扫描器。
